# Training Data Specification v1

This document defines the v1 training data format for APK row-level ML tasks.
Training data is produced by the dataset builder after it calls
`build_model_features()`.

## 1. Training Sample Format

Each training sample is one JSONL record:

```json
{
  "sample_id": "com.example.app__v1.0__abc123",
  "row_type": "filter",
  "features": {
    "component_type": "service",
    "permission": "<NONE>",
    "exported": true,
    "protected": false,
    "has_action_android_intent_action_view": true
  },
  "label": 1,
  "label_source": "rule_weak_label",
  "split": "train"
}
```

Top-level fields:

| Field | Type | Values | Description |
| --- | --- | --- | --- |
| `sample_id` | `str` | `{package_name}__{version_name}__{apk_sha256[:8]}` | Generated by the dataset builder when collecting APKs. |
| `row_type` | `str` | `filter`, `resolution` | `intent` rows are not included in v1 training. |
| `features` | `object` | See section 2 | Row-specific model input features. |
| `label` | `int` | `0`, `1` | Weak label generated by the dataset builder. |
| `label_source` | `str` | `rule_weak_label` | v1 uses only rule-based weak labels. |
| `split` | `str` | `train`, `val`, `test` | Dataset split assigned at APK level. |

## 2. Features

### 2.1 filter_row Features

`filter` training samples use the following fixed fields plus dynamic multi-hot
fields copied from `build_model_features()` output.

Fixed fields:

| Field | Type | Missing Value | Description |
| --- | --- | --- | --- |
| `component_type` | `str` | `<NONE>` | One of `activity`, `service`, `provider`, or `receiver`. |
| `permission` | `str` | `<NONE>` | Component `android:permission` value. |
| `exported` | `bool` | Required | Whether the component is exported. |
| `protected` | `bool` | Required | Whether the component has permission protection. |

Dynamic multi-hot fields:

| Prefix | Type | Missing Field Semantics |
| --- | --- | --- |
| `has_action_*` | `bool` | Missing fields are treated as `False`. |
| `has_category_*` | `bool` | Missing fields are treated as `False`. |
| `has_data_type_*` | `bool` | Missing fields are treated as `False`. |

`exported` and `protected` appear both in `features` and in the label
definition. This is a known data leakage risk. The v1 model accepts this
limitation, and Task 8 must explicitly call it out in the experiment report.

### 2.2 resolution_row Features

`resolution` training samples use:

| Field | Type | Missing Value | Description |
| --- | --- | --- | --- |
| `match_action` | `bool` | Required | Whether intent and filter actions match. |
| `match_category` | `bool` | Required | Whether intent and filter categories match. |
| `match_type` | `bool` | Required | Whether intent and filter MIME types match. |
| `caller_permission` | `str` | `<NONE>` | Caller-side permission. |
| `callee_permission` | `str` | `<NONE>` | Receiver-side permission. |
| `risk_hint` | `str` | `<NONE>` | Weak risk hint such as `IPC_SERVICE_HIJACK`. |

The resolution_row model framework is implemented in Task 6 but remains
pending v2. In v1, `intent_row` records are inferred 1:1 from `filter_row`
records and the sender is `<UNKNOWN>`, so `match_*` fields are always `True`
and have no discriminative value.

## 3. Label Conversion Rules

The dataset builder generates labels. Parser and encoder code must not generate
labels.

### filter_row

```python
label = 1 if (row["exported"] == True and row["protected"] == False) else 0
```

### resolution_row

```python
label = 1 if (row["risk_hint"] is not None and row["risk_hint"] != "<NONE>") else 0
```

### intent_row

v1 does not generate labels for `intent_row`, and `intent_row` records do not
enter the training dataset.

## 4. Split Rules

Splits are assigned at APK level:

- Split unit: one whole APK. All rows from the same APK must stay in the same
  split.
- Ratio: `train` 70%, `val` 15%, `test` 15%.
- Method: shuffle the APK list, then split by ratio.
- Random seed: `random_state=42`.
- Forbidden: do not split by row. Row-level splitting can place rows from the
  same APK in both train and test sets, causing data leakage.

## 5. Class Imbalance Handling

The v1 dataset is expected to have fewer than 50% positive samples because real
APKs do not export every component without protection.

All v1 model training uses:

```python
class_weight='balanced'
```

This is a fixed trainer default and does not depend on the observed dataset
distribution.
